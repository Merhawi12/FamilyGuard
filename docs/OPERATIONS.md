# Operations

## Where things are

| Thing                | Location                                                        |
| -------------------- | --------------------------------------------------------------- |
| API logs             | Cloud Logging, resource `cloud_run_revision`, service `parentix-<env>-api` |
| Database logs        | Cloud Logging, resource `cloudsql_database`                     |
| Metrics              | Cloud Monitoring — request count, latency, instance count        |
| Application secrets  | Secret Manager, `parentix-<env>-*`                               |
| Images               | Artifact Registry `parentix-<env>/api`, tagged with the commit SHA |
| Terraform state      | `gs://<project>-parentix-tfstate` (versioned)                    |

```bash
gcloud run services logs read parentix-prod-api --region us-central1 --limit 50
```

Logs are one JSON object per line, so the fields are queryable directly in the
Logs Explorer:

```
resource.type="cloud_run_revision"
jsonPayload.level="error"
```

Every response carries `X-Request-Id`; the same value appears as `requestId` on
any 5xx log line, which is the fastest way to get from a user report to a cause.

## Health

| Endpoint      | Meaning                                                   |
| ------------- | --------------------------------------------------------- |
| `/api/health` | The process is up. This is what the startup and liveness probes check. |
| `/api/ready`  | The process is up **and** the database answers.           |

A revision failing `/api/health` at startup never receives traffic — the previous
revision keeps serving. `/api/ready` returning 503 while `/api/health` is fine
points at Cloud SQL or the service account's `roles/cloudsql.client` grant, not
the application.

## Secrets

| Secret                 | Rotatable | Consequence of rotating                                |
| ---------------------- | --------- | ------------------------------------------------------ |
| `JWT_SECRET`           | Yes       | Every session is invalidated; all users must sign in again |
| `FIELD_ENCRYPTION_KEY` | **No**    | Every encrypted column becomes permanently unreadable   |
| `STRIPE_*`             | Yes       | Update in the Stripe dashboard first, then here         |
| `SMTP_*`               | Yes       | No user-visible effect                                  |
| Database password      | Yes       | Rotate in Cloud SQL and Secret Manager together         |

Add a new version rather than editing in place — Cloud Run reads `latest`, and
the old version stays available for a rollback:

```bash
printf 'new-value' | gcloud secrets versions add parentix-prod-smtp-pass --data-file=-
gcloud run services update parentix-prod-api --region us-central1   # picks it up
```

`FIELD_ENCRYPTION_KEY` is generated by Terraform as a `random_id`, which holds
its value in state and never regenerates on its own. Do not taint it.

## Migrations

Migrations run automatically as each Cloud Run instance starts, wrapped in a
Postgres advisory lock so simultaneously starting instances cannot race.

To inspect or drive them by hand, connect through the Cloud SQL Auth Proxy:

```bash
cloud-sql-proxy "$(terraform -chdir=infrastructure/gcp output -raw sql_connection_name)" &
export DATABASE_URL="postgresql://parentix:$(gcloud secrets versions access latest \
  --secret=parentix-prod-db-password)@127.0.0.1:5432/parentix"

npm --prefix services/api run migrate:status
npm --prefix services/api run migrate
npm --prefix services/api run migrate:down   # reverts the most recent one
```

Writing a new one: add `src/db/migrations/000N-description.js` exporting `up` and
`down`, both taking a Sequelize `QueryInterface`. Make `up` idempotent — check
`describeTable` before adding a column — so a partially applied deploy can be
retried safely. Table *creation* does not belong in a migration; add the model
and `sync()` will create it.

Take an on-demand backup before releasing anything destructive:

```bash
gcloud sql backups create --instance parentix-prod-pg \
  --description "pre-release-$(date +%Y%m%d%H%M)"
```

Point-in-time recovery is on, so you can also restore to any second within the
retention window without a manual backup existing.

## Scaling

Cloud Run scales on concurrent requests, between `api_min_instances` and
`api_max_instances` in `infrastructure/gcp/envs/<env>.tfvars`, with up to 80
concurrent requests per instance.

**Running more than one instance requires Redis.** Socket.IO events would
otherwise stay on the instance that emitted them, and a parent connected
elsewhere would silently miss alerts. `redis_enabled` and `api_max_instances`
must be raised together.

For a temporary bump without a Terraform apply:

```bash
gcloud run services update parentix-prod-api --region us-central1 \
  --min-instances 2 --max-instances 10
```

The next `terraform apply` will pull that back; edit the tfvars for anything
lasting.

## Common problems

**Revisions fail to start.** Read the logs. A configuration problem is explicit —
the API refuses to start with a message naming the missing variable, rather than
serving traffic with an insecure default. The usual cause is a placeholder still
sitting in `FIELD_ENCRYPTION_KEY` or an unset database secret.

**502/503 from the load balancer on `/api/*`.** Either no revision is serving, or
the serverless NEG is not attached. Check
`gcloud run services describe parentix-prod-api --region us-central1`.

**HTTPS does not work at all on a new deployment.** The managed certificate is
still provisioning. It cannot issue until all three hostnames resolve to the load
balancer IP:

```bash
gcloud compute ssl-certificates describe parentix-prod-cert --global \
  --format='value(managed.status,managed.domainStatus)'
```

**Realtime works for some parents and not others.** Almost always Redis: more
than one instance with `REDIS_URL` unset. Confirm `redis_enabled = true` and that
the VPC connector exists.

**Websockets disconnect after a few minutes.** Check that the Cloud Run request
timeout and the load-balancer backend timeout are both 3600s. The shorter of the
two wins.

**Email is not arriving.** Check `EMAIL_PROVIDER` is `smtp` and that the
`smtp-host` secret holds a real value rather than the placeholder. With
`EMAIL_PROVIDER=none` the API logs verification codes and reset links instead of
sending them, which is the intended local behaviour but wrong in production.

**Uploads fail with 503.** `STORAGE_PROVIDER` or `GCS_BUCKET` is unset.

**Uploads fail with 403 when signing.** The service account is missing
`roles/iam.serviceAccountTokenCreator` **on itself**. Signed URLs on Cloud Run go
through the IAM `signBlob` API because Application Default Credentials carry no
private key, and the error message does not mention signing. A 403 on the `PUT`
itself instead means the URL expired (default 5 minutes) — the client should
request a fresh one.

**A user cannot sign in after a password reset.** Expected: a reset revokes every
existing session by design.

## Staff accounts

There is no sign-up for staff. Create or promote an account with:

```bash
node services/api/scripts/create-admin.js --email person@example.com --name "Name"
node services/api/scripts/create-admin.js --email person@example.com --role support
```

Against production, run it through the Cloud SQL Auth Proxy (see
`docs/DEPLOYMENT.md` §1.6); the generated password prints once. Re-running
promotes an existing account without touching its password unless one is
explicitly supplied.

To set the password yourself, use `--password-stdin` or the `ADMIN_PASSWORD`
environment variable. Avoid `--password <value>`: it is captured in shell history
and visible in `ps` output to other users on the host.

To demote someone, change their role from the Admin Dashboard rather than with
this script, so the change is captured in the audit log.

## Access review

The Admin Dashboard is staff-only and marked `noindex`. Two independent gates:
the API checks role and permission on each call, and the console refuses to mount
for a non-staff token.

Audit logs (`/api/audit`, surfaced in the console) record authentication events,
role changes, plan changes and force-logouts. Review them after any staff
offboarding, and revoke the departing account's sessions:

```
Admin Dashboard → Sessions → Force logout
```

Review Google Cloud IAM at the same time — anyone with `roles/run.admin` or
`roles/secretmanager.secretAccessor` on the project can read production secrets.
